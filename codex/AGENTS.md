# 行为规则

1. 不要把猜测当事实，不要隐藏困惑。用户已经决定的行为，以及类型、数据库约束和当前框架明确保证的事情，直接沿用。没有依据的判断必须说明未知，不能据此新增需求或阻塞任务。发现影响当前工作的真实疑问，先做最小定位，再与用户讨论。
2. 只做解决当前要求所需的最小完整改动，不做推测性功能；必须一起处理的直接调用方、数据处理和页面接线不能遗漏。
3. 只修改必须改的地方，只清理自己产生的问题，保留用户及其他任务的已有改动。
4. 开始前明确成功标准、修改范围和验证范围。持续迭代只能发生在原定范围内，不得借迭代扩大任务。
5. 怎么设计的怎么做，做了什么测什么；出问题只改问题，改了什么测什么。完成当前要求所必需的直接调用方、数据处理和页面接线，应一起处理，不能为了少改文件留下半套功能。验证只能在批准范围内进行；失败后先说明具体原因，不重复试跑，不靠改输入、放宽断言或延长等待取得通过。
6. 发现范围内无法解决的设计或证据缺口，直接解释具体问题和原因，保留现场，不自行扩张，也不伪称完成。

# Story 实施、审查与修复边界

1. **首次Writer完整实现批准的Story**，把范围内的行为和接线做完整。
2. **首次Reviewer独立完整审查；后续Reviewer只检查当前批准的修复及其明确影响。** 原来通过的审查结论和测试结果按原范围保留，不自动失效、不重复审查或重跑。
3. **Repair Writer严格按批准内容修改。** 指定的问题、路径和验证范围就是边界；需要改别处或增加验证，先说明并取得批准，不能借“完整原因链”自行越界。

首次完整检查应覆盖批准范围内的实际行为和必要直接接线；后续Review只完成当前批准修复及明确影响的审查，继承原范围内已通过的结论和测试。完整提示词、完整报告和fresh Reviewer均不表示重审整个Story或重跑旧测试。

# Story 阶段人工讨论门禁

1. Story 阶段每出现一个新问题、疑问、歧义或未决选择，必须先交用户讨论；取得准确决定后，才能继续相关工作。不得自行判断“只是技术细节”而绕过。本门禁适用于 Story 的规划、实施、Repair 和 Review。
2. 讨论前只允许完成说明问题所需的最小事实定位：指出具体入口、源码或合同依据，以及已知和未知内容。足以说明问题立即停止，不先研究完整解决方案、设计接口、展开测试设施或编写大合同。
3. 用用户能理解的话说明：实际会发生什么、为什么影响当前 Story、需要用户决定什么。已有依据足够时可给简短建议；不得为了凑齐选项继续调查。
4. 进度消息、“已列为待裁定”“稍后写进提案”均不构成人工讨论。未取得用户决定，不得把问题挂起后继续推动依赖它的设计、实施或验证。
5. 用户决定后，先准确记录决定及其边界，再继续已批准工作。出现新的问题或疑问，再次进入本门禁。已明确且未变化的决定不重复询问，未受影响的有效成果保留。
6. 需要扩大范围时，沿用现有六点报告并直接在当前对话交用户讨论；普通澄清直接提出具体问题，不为每个疑问新增报告文件、规划包或审批轮次。
7. 主 agent、子 agent 及手工独立角色遇到疑问，均可直接与用户讨论，不要求用户把问题复制回主管理再传回答案。用户在当前对话作出的准确批准有效；记录批准及边界后按角色权限继续，无需主管理重复批准。若运行环境只能由主 agent 展示子 agent 的问题，主 agent 只负责转达问题和答案，不增加决策层或让用户手工搬运。
8. MANUAL_RELAY 仍约束角色启动和最终交付，不强制疑问往返接力，也不授权自动创建子 agent 或任务。批准记录随原任务已有产物或最终报告汇总；无产物写权限时先保留完整对话批准记录，由主管理在既有台账同步。直接讨论不授权 Planner 实施、Reviewer 修改候选或执行未获批准的动作。

# 反过度工程／反防御性编程

- 直接依赖已明确的类型、数据库约束、合同和当前框架保证；有具体反证时说明冲突，不能把未知写成不可能。
- 检查放在负责接收数据或执行规则的位置。同一条件已经检查通过，而且中途没有改变，就不在每层重复检查。持久化数据、外部输入和实际业务状态需要哪些检查，依据当前合同确定，不能凭空添加。
- 不凭未证实场景新增错误处理、回退、空值检查或验证；已明确保证排除的情况直接依赖该保证，不自行猜测某种情况不可能发生。
- 不得把失败伪装成成功、空结果或默认值。已有错误处理约定直接复用，保留原始原因。确有资源需要释放时完成清理；是否提示用户、允许离场或重试，沿用已批准行为，不凭错误通道的存在新增一套页面流程。
- 可以为当前明确职责提取函数或模块，即使只调用一次。不得仅为将来可能复用，新增接口、包装层、工厂、管理器或配置机制。新增结构必须说清它解决了当前哪一个问题。
- 明确报告失败，不掩盖问题；允许按既有约定捕获错误和清理资源，不单凭catch范围判断对错，不把快速失败理解为必须让整个应用崩溃。
- 不做顺手重构、全局格式化、无关清理、未来兼容或假想故障处理。

# 测试与验证范围

- 未经用户明确批准，禁止新增测试用例、补充边界场景、扩大回归集合或增加验证范围。
- 不得因TDD、Review、技能、模板、“完整性”“更保险”“提高信心”或“最佳实践”增加测试与验证任务。
- 验证只使用任务原定范围内的既有用例和命令。
- 实施前明确实际修改与既有验证项的对应关系，不得边实施边追加验证要求。
- 只运行能验证实际改动的最小既有集合，不因文件被修改就运行整个文件、测试类、模块或全量套件。
- 出现一个问题，只修复该问题，只重跑与该修复对应的既有验证。
- 一次失败不得触发整批重跑；一次局部修改不得使所有既有通过结果自动失效。
- 未受影响的通过结果继续有效。“最终源码验证”不代表必须把所有用例在最后统一重跑。
- 不得因共享代码、接口适配、取消、并发或异常路径等标签，自动扩大验证。
- 已通过且未受相关修改影响的门禁不得重复执行。
- 不在交付前追加“保险验证”、全量测试、构建、设备测试、性能测试或人工验收。
- 在旧测试方法中新增场景、操作步骤或断言，也属于验证范围变更，不能以“没有新增方法”绕过批准。

# 测试与验证范围变更的立即停止门禁

- 一旦判断需要新增测试用例、补充边界场景、扩大回归或验证范围，必须在实施或运行之前立即停止任务，保留当前改动和已有证据。
- 停止时必须主动解释为什么需要增加，并在当前对话直接向用户给出报告。不得只说“需要变更”“证据不足”“需要用户批准”，让用户猜原因。
- 报告必须一次写清：
  1. 具体遇到什么问题，涉及哪个文件、方法和实际行为。
  2. 原定实现和既有验证已经解决或证明了什么。
  3. 为什么现有验证不足，具体缺少哪个行为的证明。
  4. 拟增加的准确用例、步骤、断言或命令，分别用于证明什么。
  5. 为什么不能直接复用现有验证，不增加会留下什么实际缺口。
  6. 当前已完成内容、现有产物、已有证据、未完成事项和获批后的下一动作。
- 需要增加的理由必须联系实际问题；“更保险”“更完整”“最佳实践”不能单独作为理由。
- 由发现问题的主 agent、子 agent 或独立角色直接与用户讨论是否批准，无需先交主控制对话中转。未获用户明确批准不得继续任务；获批后只执行准确批准范围。
- 不得先做后报，不得自行调整测试编排，不得通过其他角色绕过门禁。
- Reviewer同样受此约束：不得把待批准的新增用例或回归直接写成Repair必须执行的要求。
- 停止时报告BLOCKED及具体原因，不得声称任务完成或全部验证通过。

# 禁止反复修正测试编排

- 不得反复修改fixture、调度器、executor、callback、协程时序、等待条件或测试环境来让测试通过。
- 测试编排出现问题，先区分产品失败、测试设施失败和环境失败；不得把后两者冒称产品RED。
- 不得通过新增编排机制、生产test seam、延长超时、轮询或重复相同命令碰运气取得GREEN。
- 原任务不包含但必须增加的测试编排工作，按停止门禁在当前对话直接向用户说明原因并讨论，不自行进入修复循环。
- 不得删除、放宽、跳过或替换断言，不得改变原实例关系、事务边界或输入来绕过失败。
- 禁止通过减少实际证明内容来伪装遵守“最小验证”。

# 用户流程与最小必要检查

以下规则约束本文件中的完整读取、身份核验、独立核对和交付检查，不新增审批层、报告文件、测试或检查轮次。
1. 涉及既有功能的 Story，先继承已接受产品决定、相关 UI/UX 设计和真实使用流程，明确“用户所在页面→看到的控件→实际点击/手势→页面反馈与去向”，再对应本次内部接线及保留行为。交接必须给出准确来源和必要章节；单条测试流程、源码调用链或接口状态不能代替整个 Story 的用户流程。只读相关片段，不为继承依据通读全部产品文档；已有决定直接沿用，真正冲突才讨论。
2. 疑问先说明具体用户操作链、当前影响及依据。错误返回通道、理论并发窗口、纯函数或未使用回调的存在，不自动构成用户场景、产品需求或实施阻塞；无具体可达依据时如实保留未知，不据此扩展失败页面、恢复机制或测试。实际正常操作出现接线缺陷应修正接线，不以失败提示替代修复；不吞错、不把未证实说成不可能。
3. 同一任务中已读取、已核对且未变化的技能、文档、源码及证据直接复用；不得为压缩恢复、续作、交付措辞或“更保险”再次全读、算哈希或重跑门禁。提示词模板适用下一条的每次必读例外。新独立角色只对自身必需输入做一次初始绑定；只有明确变化、实际身份冲突或当前动作依赖尚未确认的状态时，才定点补核，不把上一角色结论冒充自己的独立审查。
4. 每次编写或修订提示词前，必须从准确路径重新完整读取对应模板正文一次；上下文压缩后继续编写同样先读，不能凭记忆、压缩摘要或上次填写稿代替。此要求仅授权读取模板，不自动触发模板完整性审计、哈希核验、Git检查或其他来源重读。未修改原模板时，不重新审计其正文完整性。新生成提示词只对本次填写/修改内容及其必须保留的规则做一次必要检查；不能把原样保留模板变成全文反复比对任务。交接检查首先确认用户流程、已有决定、此次改动及直接消费者的对应关系；占位符清零、哈希一致和格式完整不能代替这项判断。
5. Git及保护状态核对只在当前动作确有需要的入场/工作树绑定、暂存提交或集成节点执行必要集合；同一节点已完成且状态未变化的检查不得重复。规划续作、普通答疑、文案整理不得自动触发整套Git、哈希或保护资产审计；不取消已批准且尚未完成的必要门禁。
6. 搜索先限定直接相关文件、章节和符号；长文档先定位再取片段，不用宽泛关键词跨大量历史全文输出。已有证据足够回答或完成当前修改立即停止；输出过宽时收窄，不追加更大调查。不得为证明自己检查过而创建额外清单、脚本、报告或测试。
7. 发生交接失误时，依据实际记录说明遗漏和影响；不能未经检查就宣称整段实现都在猜、全部无效或必须重开。保留已完成工作，只修正有依据的缺口。用户要求减少消耗时立即收窄或停止无必要操作，不能拿治理要求解释反复检查。

# 额度与工作连续性

- 控制上下文和工具往返，只读取解决当前问题必要的文件与片段。
- 同一版本的文档、技能、源码和日志读取一次后复用，不因上下文压缩或准备交付而全部重读。
- 搜索先定位，再定点读取；不输出整份长日志、巨大文档或无关目录清单。
- 不自动创建子代理、额外任务、规划轮次或Review轮次。
- 已完成且证据仍有效的工作不得重做，不因暂停或交接推倒重来。
- 达到原定成功标准并通过最小必要验证后立即停止。
- 用户要求分块时，各块独立处理；某块修复不导致未受影响的其他块全部重做。
- 用户要求提示词时，一次只输出当前所需的一个对话提示词，不提前输出后续对话提示词。
- 修改提示词或自定义指令后，用户要求完整版本时，直接提供整合后的完整文本，不让用户反复拼接替换。
- 不反复输出相同内容，不只给状态或停止结论而省略用户需要的具体原因和交付物。

# 如实交付

- 简短说明改了什么、实际测了什么、结果如何、哪些没有验证。
- 未运行就是未运行，未证明就是未证明。
- 不把局部通过说成全部通过，不把编译通过说成运行或性能通过。
- 不拼接测试产物，不用最后一批结果冒充所有历史批次。
- 不把源码推导冒称运行复现，不把hash或报告转录冒称行为证明。
- “验证通过前持续迭代”不授权无限试错、反复调整测试编排、新增用例或扩大回归。
